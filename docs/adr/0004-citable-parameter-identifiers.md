## Context

The reference resources this project would need to resemble — CVE, ATT&CK — did not win
on data quality. They won by becoming **the thing people cite**. CVE's value is the
identifier itself: an unambiguous, permanent handle that lets two parties refer to the
same thing years apart.

RiskShard currently has no such handle. A parameter can be *linked* (deep links shipped
2026-07-28) but not *cited*: the link resolves to whatever the value is today, not to the
value that was there when someone wrote it down. An auditor citing a figure in a 2026
workpaper has no way to let a reviewer in 2028 confirm what it said.

Two prerequisites are already in place, which is why this is worth doing now rather than
later:

- **Reproducibility** (ADR-0002) — the same shard now yields the same number on any
  machine, so a cited figure is verifiable by a third party.
- **Immutable releases** — `data_pack_releases/*.json` already pin a file set with a
  SHA-256 fingerprint (e.g. `2026.07.21-v0.1.0-stable`, 69 files, `ff9b713d…`).

## Decision

Introduce a citation scheme with an explicit permanence guarantee.

### Identifier form

```
RS:<shard_id>/<parameter>                      canonical (tracks latest)
RS:<shard_id>/<parameter>@<release>            pinned (immutable)
```

Example: `RS:us_finance_bec_midmarket/impact.likely@2026.07.21-v0.1.0`

Readable, derived from identifiers that already exist, no central registry to operate.
The pinned form is what belongs in a document.

### Resolution

- canonical → `https://raviaxo.github.io/RiskShard/#<shard_id>/<parameter>` (works today)
- pinned → `https://raviaxo.github.io/RiskShard/r/<release>/#<shard_id>/<parameter>`

The pinned form requires publishing an **archived explorer per release**. That is cheap:
the explorer is self-contained static HTML generated by `build_explorer.py`, so the
release path writes a copy under `docs/r/<release>/` and never touches it again.

### Permanence guarantees

These are the whole point; without them the identifier is decoration.

1. **Identifiers are never reused or deleted.** A parameter that is retired keeps
   resolving and is marked superseded, with a pointer to what replaced it.
2. **Shard renames require an alias.** Renaming `X` to `Y` adds `X → Y` to an alias table
   so existing citations keep resolving. Renaming without an alias is a breaking change
   and is not permitted.
3. **Pinned citations are immutable.** An archived release is never regenerated. If it is
   wrong, the correction is a new release plus a `revisions/` entry — never an edit in
   place.
4. **Integrity is checkable.** Each release already carries a fingerprint, so a reader can
   verify the pinned artefact is the one that was cited.

### Cite-this affordance

Each parameter offers a formatted citation for pasting into a workpaper or deck:

> RiskShard `RS:us_finance_bec_midmarket/impact.likely@2026.07.21-v0.1.0` — impact.likely
> = USD 123,005 (FBI IC3 2025 Annual Report, Apr 2026). Caveat: IC3 is a self-reported
> complaint population; not financial-services-specific, not mid-market-specific, not a
> full loss distribution. Retrieved 2026-07-28.

The caveat travels **inside the citation**. Someone quoting the number in a board deck
carries its limitation with it, which is the behaviour this project exists to produce.

## Consequences

- The release path grows a step (archive the explorer); `docs/` grows by roughly the size
  of one HTML file per release — tens of KB, negligible.
- A rename policy becomes binding. That is a real constraint on future refactors, and it
  is the price of permanence.
- Nothing about existing evidence changes; this is addressing and packaging.

## Alternatives considered

- **Sequential opaque IDs (`RS-0001`), CVE-style.** Survives renames without an alias
  table, but needs an assignment registry and discipline to operate, and reads as
  meaningless in a document. The alias table is the cheaper way to buy the same property.
- **Content-hash identifiers.** Perfectly immutable, but a citation would change whenever
  a caveat was reworded, and it is unreadable.
- **Do nothing, rely on deep links.** They already work for conversation. They cannot
  support a citation that must still resolve correctly in two years, which is the use
  case that makes a reference canonical.

## Recommendation

Adopt. It is small, mostly mechanical, and it is the difference between a tool people
look at and a reference people cite. Sequence it before broad shard expansion: a large
portfolio without stable identifiers is harder to retrofit, and coverage is only valuable
if what it covers can be pointed at permanently.

## Implementation (2026-07-29)

- `build_explorer.py` resolves the newest `data_pack_releases/*.json` and pins every
  citation to it; `--archive` writes `docs/r/<release>/index.html` and **refuses to
  overwrite an existing archive**, enforcing guarantee 3 in code rather than in prose.
- The archived copy reaches the shared fonts via an `--asset-prefix` of `../../`, so an
  archive costs one HTML file (~66 KB) and ships no duplicate assets.
- `aliases.yaml` (repo root) is consulted when a hash does not match a known shard, so a
  renamed shard keeps resolving. Empty today — nothing has been renamed.
- Each parameter shows its identifier and offers **cite this number**, which copies the
  value, source, publication date, caveat and the canonical pinned URL. Money is rendered
  with its currency code rather than the raw unit, and the URL is always the canonical
  site — never the host the reader happens to be viewing (a local copy or a fork).
- Wired into the release checklist in `BENCHMARK_CONTRIBUTOR_WORKFLOW.md`.

**Open questions resolved by implementation:** the archive publishes for every release
that has an artifact (not only tagged ones), and the alias table lives in the repo root.

**Still open:** whether canonical (unpinned) citations should be actively discouraged in
documents, and whether parameter-level retirement needs its own superseded-by table — no
parameter has been retired yet, so guarantee 1 is currently policy rather than mechanism.
